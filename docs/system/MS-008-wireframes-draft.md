# MS-008 | Approved responsive wireframes

The user approved these bilingual wireframes and the four lead journeys on 2026-11-26. The specification covers REQ-008 and both work packages. Each content slot requires authorized material before public use. Engineering verifies the implemented patterns and accessibility in MS-010 through MS-013.

## Shared frame

Wide layout: skip link → brand, primary navigation and utilities → breadcrumb when relevant → page heading and introduction → main sections → relevant next action → footer. Split leads may pair content and evidence media. Lists use multiple columns only when cards retain readable widths.

Compact layout: skip link → brand and menu disclosure → breadcrumb → heading and summary → primary action → media and remaining content → footer groups stacked. Intermediate widths can fit two columns. At 320 CSS pixels, use one column, wrapping text and reflowing controls. Content order follows reading and tab order. Preserve access to footer privacy, terms and language links from both layouts.

Use the same logical order in Arabic and English. Arabic uses RTL with breadcrumbs, directional icons and placement mirrored. Keep logical keyboard order, numerals, identifiers and media direction correct. Mark embedded foreign-language text where appropriate. Reserve image space only for approved media, with descriptive localized alternatives or an empty alternative for decorative images.

## Navigation interaction

On wide screens, approved categories use links or button disclosures. A grouped panel can place sections and featured destinations in columns, with headings and links in document order. Compact screens use a drawer with the same destinations grouped vertically. Give disclosures an accessible name and expanded state. Escape closes the panel, and closing an overlay restores focus to its trigger. Keep primary links available without hydration. Offer the language switch for an approved matching translation, with a localized unavailable message when a match is unavailable. Avoid hidden keyboard traps and hover-only controls.

## Four lead journeys

| Journey         | Entry and return                                                   | Intake purpose                                           |
| --------------- | ------------------------------------------------------------------ | -------------------------------------------------------- |
| General inquiry | Header or footer → PG-019 → PG-026 → home or contact               | Route a general corporate request.                       |
| Consultation    | Solution or service → PG-020 → PG-026 → relevant capability        | Capture enough approved context to route a consultation. |
| BIM demo        | Home or BIM flagship → PG-021 → PG-026 → BIM flagship              | Route demo requests according to confirmed availability. |
| Partnerships    | Approved partnership link → PG-022 → PG-026 → partnerships or home | Route a partnership request to the approved owner.       |

Each form shows a purpose heading, approved fields with persistent labels and required indicators, privacy notice, and a single submit action. Field lists and recipients are owned by the lead contract and content approval process. Use a single-column reading order on compact layouts. On wide layouts, companion context may sit alongside the form. Keep inputs with their help, errors and labels at every width.

| State                                 | Expected behavior                                                                                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Ready                                 | Describe the request purpose and data usage before submission.                                                                  |
| Invalid                               | Keep entered values, show a summary linked to invalid fields and inline messages, and move focus to the summary.                |
| Sending                               | Prevent duplicate submissions and announce progress without shifting focus or layout.                                           |
| Accepted                              | Navigate to PG-026 after confirmed acceptance and announce the outcome.                                                         |
| Network, server or rate-limit failure | Preserve editable fields, show an actionable localized message and provide retry or a verified alternate channel as applicable. |
| Unavailable                           | Hide inactive submission controls and show an approved alternative when available.                                              |

## Review and handoff

Candidate components include the shared shell, navigation disclosure and drawer, language switch, breadcrumbs, section leads, media pairs, cards, lists, CTA links, pagination, resource links, FAQ disclosures, field groups, error summary, live status and confirmation panel. Reuse suitable starter components after comparison against their [component map](../astro/COMPONENT-MAP.md). The [accessibility standard](../standards/astro/ACCESSIBILITY-STANDARD.md) governs the review.

Design review must cover each PG row and all four journeys in Arabic and English at compact, intermediate and wide widths. Check reading order, 320 px reflow, large text, visible focus, keyboard and screen-reader behavior, reduced motion, translatable strings, media rights and failure states. Record the reviewed revision, open decisions and designer/technical lead approval before handing approved patterns to MS-010 and MS-012.
